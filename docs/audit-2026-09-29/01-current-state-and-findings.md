## 2. 现有结构

  独立配置格式 / 视觉步骤 / 点击后确认 / 总量限制

值得保留的基础：worker-object + QThread 模式、`threading.Event` 停止标记、线程之间信号传递、执行前复制流程、延迟加载 OCR/YOLO、PNG 字节编解码、JSON 暂存文件替换和复制失败回滚、已有图片与输入回归测试。不是从零重做。

主要耦合：一个新增节点要同时修改默认值、运行分发、编辑字段、显隐、导入、流程校验、导出和素材同步。此次发现的 YOLO 校验/模型路径遗漏正是这种耦合的实际后果。

### F02：停止请求不能覆盖整个操作边界

- 位置：`app.py:2814`、`3822`、`3954`、`3975`、`4627`、`7815`、`9238`。
- ADB 使用阻塞 `subprocess.run`；单次输入通常超时 8 秒，长拖拽最高 600 秒并额外等待 8 秒。设置停止标记不会主动打断当前子进程调用。
- `_capture_window()` 先调用同步 `PrintWindow`，即使已知 ADB 可用也不会直接绕开它。Win32 官方说明该 API 是阻塞调用，不能把它等价为有确定超时的函数。[S1]
- `_wait_for_yolo()` 在推理结束返回结果前没有再次确认停止；合成探针在 `detect()` 中触发停止后，仍观察到后续 `_mouse_action` 分发。探针没有发送真实输入；ADB 自身有发送前检查，但 Win32 路径未统一保护。
- `_wait_for_window_tasks()` 最多等待 1.5 秒，没有把“还有线程未退出”作为关闭阻断条件。`closeEvent()` 随后接受关闭。模拟未结束任务可复现这一决策；运行中的 QThread 生命周期需要等待 finished 后回收。[S2]
- 修复方向：统一取消/时限上下文，所有外部调用返回后和动作分发前检查；ADB 命令可取消并回收管道；不可可靠中断的本地 API 使用受控进程隔离；关闭采用异步等待状态，禁止强杀 QThread。
- 注意：终止本机 ADB 客户端不保证撤销已在安卓端开始的手势。停止语义应保证“不再分发新动作”，并报告已提交动作的有限残余时长。

### F01：YOLO 判断可编辑但不可启动

- 位置：`app.py:1424` 的 `validate_flow()`；启动调用位于 `app.py:7637`。
- 校验器对所有 condition 只检查是否存在非空 `image`，没有按 `yolo_exists` 校验 `model/target_class`。
- `F01_yolo_condition_rejected` 探针结果：合法连线的 YOLO 判断返回“至少需要一张模板图片”。补上任意操作节点也不会消除该校验错误。
- 现有 YOLO 测试覆盖了界面编辑与导入，没有通过真实启动校验路径。
- 修复方向：条件按类型分派校验；图片条件保留模板要求，YOLO 条件校验模型、类别和阈值。增加“编辑 -> 保存 -> 重开 -> 校验 -> 运行”的整链路测试。

### F03：相对模型路径重写不完整

- 位置：`app.py:8944`、`9037`、`9061`。
- 素材导出支持模型，但 `_sync_exported_image_paths()` 只同步 `image`。
- 触发：模型使用指向源目录之外的 `../...` 相对路径，导出到另一目录时被改成 `script_assets/...`。
- 结果：导出的 JSON 用新路径，内存与随后的自动草稿保留旧模型路径；`current_file` 已切换到新目录，后续执行/再次导出可能找不到模型。
- 已复现内存路径与导出路径不一致。普通 `game.onnx` 同名路径没有重写，现有测试仅覆盖此较简单情况。
- 修复方向：使用统一素材引用遍历器同步 `image/model`，按 task/node ID 对齐，不只依赖列表下标；覆盖动作、判断、中文目录、外部相对路径、同名文件冲突及第二次导出。

### F04：否定条件不能把异常当成真

- 位置：`app.py:2632`、`2655`、`2704`、`4627`。
- 缺失模板或模板读取失败直接返回 `False`；外层 `negate=True` 会变成 `True`。探针已复现“模板文件不存在 -> 非条件成立”。
- YOLO 连续截图失败最终也被包装为“检测超时”，`_condition_yolo_exists()` 再通过中文“超时”子串将其解释为不存在。错误类型与日志文本绑定。
- 当前与/或使用列表推导先运行全部条件，每个条件有自己的截图与等待周期；不仅不能短路，而且不保证多个条件来自同一帧。
- 修复方向：至少区分 FOUND / NOT_FOUND / ERROR / CANCELLED；只有明确 NOT_FOUND 才可取非。新增同帧判断应作为明确语义选项，不能不经迁移就改变旧脚本的时间窗口语义。

### F05：模型加载需要明确协议，不能凭维度猜测所有格式

- 位置：`yolo_runtime.py:29`、`67`。
- 输入仅检查一个四维张量；没有核对 dtype、batch、通道顺序、任务类型、输出数量和实际类别数。
- 推理固定生成 FP32 NCHW 输入；输出取第一个张量，根据维数猜测普通检测或 6 列结果。
- 合成 objectness 输出 `[cx,cy,w,h,obj,cls0,cls1]` 中，目标 cls0 实际分数为 `0.99 * 0.01 = 0.0099`，代码却报告约 `0.99`。这说明不受支持的导出格式没有被拒绝，不代表已经在真实游戏发生误点。
- FP16、分割/姿态、不同批次和导出版本同样需要明确支持/拒绝规则。不能认为“.onnx 后缀正确”就代表解码协议相同。Ultralytics 的精度、动态形状和 NMS 导出选项确实会影响部署契约。[S5]
- 修复方向：先限定可验证的 detect 协议，元数据加 manifest 声明，严格预检；不支持的模型在任何截图/输入前拒绝。
- 扩展方向：经相同输入预处理的原框架推理结果与 ONNX 结果做黄金集对照，而不只是 mock 张量测试。

### F06：日常任务时限与可选步骤语义存在缺口

- 位置：`game_daily.py:195`、`203`、`228`。
- `_capture()` 前后检查时限，但 `_locate()` 在 `matcher.find()` 后未复查；点击前可能还有一次 after 检测，也没有统一截止时间检查。
- 虚拟时钟测试：总预算 1 秒，推理耗时 2 秒后仍观察到点击分发。随后确认失败不能撤销已经发出的动作。
- 可选步骤检查也有缺口：局部识别期限 0.5 秒，截图耗时 0.6 秒，而总任务预算尚有 10 秒时，直接抛“超过任务时限”，不是返回未找到后跳过可选步骤。
- 修复方向：区分任务总 deadline 与步骤 deadline；截图、推理、确认返回后及输入前统一检查；局部超时可按 optional 处理，总超时/设备失败/取消不能被跳过。
- CLI 的窗口初始化和查找发生在 `DailyRunner.run()` 计时之前；文档需要说明时限口径，或将其纳入统一任务预算。

### F08：自动保存缺少可验证提交与灾难恢复

- 位置：`app.py:6832`、`6854`、`6884`。
- 350 ms 防抖后全量深拷贝并序列化流程，写入同一个 QSettings draft 键；`sync()` 后没有检查 `status()`。官方提供的错误状态需要主动检查，不能只捕获 Python 异常。[S3]
- 恢复遇到部分解析错误时删除 draft，再创建空任务；尚无保留坏数据原文、上一版本或恢复入口。
- 多个应用实例使用相同设置命名空间，缺少草稿修订号/锁；可能相互覆盖，未做真实多进程试验。
- 修复方向：短期增加状态检查、原文隔离备份和错误提示；中期将业务项目放到用户数据目录，按 project ID 原子写入并保留版本，QSettings 只保存 UI 偏好。

### F09：任务对象独立不等于目标设备独占

- 位置：`app.py:4424`、`7499`、`7629`、`7637`；对照 `game_daily.py:120`。
- GUI 下拉框主要保存标题/进程条件；执行时 `_find_window()` 取第一个匹配窗口。同标题多开无法保证再次选中原实例。
- “全部运行”为所有任务创建线程，只用 `id(task)` 防止同一任务重复启动；不同任务仍可同时向同一 HWND 或 ADB serial 发送动作。
- CLI 已有“匹配实例数不是 1 则拒绝”的局部保护，但 GUI 没有复用。
- 修复方向：持久化目标选择策略、执行时解析明确实例，建立每个设备的 lease/动作队列；一个设备同一时刻只允许一个控制任务，其他排队或明确拒绝。

### F07：模板库刷新是已经测到的主线程热点

- 位置：`app.py:6580`、`6625`、`6956`、`8054`。
- `_refresh_template_library_if_ready()` 只判断控件是否创建，不判断页面是否可见或图片引用是否变化。
- 每次刷新重新枚举所有任务素材、读取原图、解码、缩放并重建列表；选中素材的详情还会再次解码。
- 本轮实测：100 张 320×180 PNG，编辑等待节点名称时解码 101 次，中位 195.583 ms，7 次采样上界 210.526 ms。素材页保持隐藏。
- 修复方向：区分结构/属性/素材变更事件，索引增量更新，隐藏页仅标记失效，缓存缩略图，后台加载 QImage、主线程创建 QPixmap。不要只是把所有 QWidget 操作整体搬入线程。

### F10：能力协商和坐标契约需要统一

- 位置：`app.py:2789`、`2931`、`2960`、`3932`、`3975`。
- 发现模拟器 backend 后普通动作优先 ADB，但 move、部分键和 Unicode 输入运行时才报不支持；宏又走 Win32。属性面板没有按设备能力提前校验。
- 截图返回 `(cv2, frame, origin)`，ADB 源尺寸、留边和 origin 分散缓存于 `last_window`；普通坐标动作与识别所得坐标没有类型区分。
- 原生屏幕坐标、窗口客户区、安卓像素、ROI 和模型 letterbox 的转换链不明确；窗口移动/旋转/分辨率变化后何时失效需要回归验证。
- 修复方向：显式 Frame + CoordinateTransform + backend capabilities，禁止暗中从某个设备失败后切到其他实例或桌面输入。
- 另需检验 ADB 文本中的 `%`、引号和 shell 特殊字符：当前空格/百分号替换不等于可靠的安卓 shell 参数编码。本轮没有实际发送特殊字符命令。

### F11：图与节点的协议校验分散

- 位置：`app.py:1215`、`1424`、`8754`、`8826`。
- 默认值、显示、运行、导入的类型分支各自维护；condition 类型陌生时可能按图片处理。
- `validate_flow()` 建字典会折叠重复节点 ID；只检查从 start 的可达性，没有对每个可达节点做“能否走到 end”的反向可达性检查。
- JSON 顶层不是对象时，`_open_script()` 在 `data.get()` 处可能抛出未被该函数捕获的 AttributeError；全局异常处理器可以提示，但缺少明确的文档格式校验与恢复语义。
- 修复方向：集中 NodeSpec 和文档 schema/migration；合法循环明确由最大步数、deadline、loop 策略保护，不使用“图上有一个 end 可达”代表全部分支可终止。

### F12：绿色测试没有覆盖完整发布路径

- 位置：`test_yolo_integration.py`、`test_game_daily.py`、`packaging_smoke.py`、`AutomationTool-small.spec`、`requirements-lock.txt`。
- 测试主要验证 mock 推理和局部函数，缺少 YOLO 判断启动、真实模型对照、停止中关闭窗口、多实例争用、资产路径重写后的草稿恢复。
- `packaging_smoke.py` 含真实 OCR，但没有真实 YOLO 推理、CLI 或 ADB 冒烟；单独打出的 smoke EXE 也不等于正式 EXE 自检。
- 更具体的问题：smoke 脚本有 6 处 `assert`，而精简 spec 设置 `Analysis(optimize=1)`；断言在优化编译时被删除，其中直接写在断言表达式里的识别调用也不会执行。本轮已用 CPython 字节码验证移除行为，未重新打包。冻结报告的 PASS 因而不足以证明这些比较成立。此次源码冒烟未开启优化，仍执行了这些检查。
- spec 只把 `app.py` 或 `packaging_smoke.py` 作为入口，`game_daily.py` 是独立源代码 CLI，尚不是现有 GUI 内完整功能。
- requirements-lock 固定顶层包，但没有所有传递依赖和哈希；README 打包流程又使用浮动 requirements。
- 本地有多个历史 dist/build；某个 EXE 存在不证明它对应当前未提交源码。2026-09-25 的 YOLO EXE 文件为 114,801,344 字节，本轮只清点，没有重新构建或再次启动。
- 修复方向：smoke 使用显式 `if ...: raise ...`，不能依赖可被优化移除的 assert；版本、Git revision、脏工作区状态、完整依赖清单、模型协议、SHA256 与测试报告绑定到每次发布；增加 Windows CI 与正式入口只读诊断模式。
